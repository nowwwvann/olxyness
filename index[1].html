    Panduan arsitektur (skala besar)

    1. Media server: pakai SFU

    Mesh (seperti versi lokal ini) hanya cocok untuk ±4 orang. Untuk puluhan peserta gunakan SFU: tiap peserta mengunggah 1 stream, server meneruskannya ke peserta lain tanpa decode ulang, sehingga CPU server ringan dan unggahan pengguna tidak membengkak. Rekomendasi: LiveKit (siap pakai, SDK lengkap) atau mediasoup (kontrol penuh, Node.js). Aktifkan simulcast agar peserta berjaringan lemah menerima kualitas lebih rendah. MCU (campur video di server) hanya untuk kebutuhan khusus seperti rekaman/siaran karena sangat berat.

    2. Basis data

    PostgreSQL: akun, grup, anggota, status. ScyllaDB/Cassandra (atau MongoDB untuk skala menengah): riwayat chat, dipartisi per channel + waktu. Redis: presence online, cache, dan pub/sub agar banyak server Socket.io tersinkron (adapter Redis). S3/MinIO: file dan gambar status. Simpan hash kode login (argon2/bcrypt), jangan teks asli.

    3. Keamanan & E2EE

    Wajib HTTPS/WSS. Media WebRTC sudah terenkripsi DTLS-SRTP, tetapi SFU bisa membuka paketnya; untuk E2EE sungguhan gunakan WebRTC Insertable Streams / SFrame dengan kunci grup. Untuk chat: protokol Signal (Double Ratchet) atau MLS untuk grup; server hanya menyimpan ciphertext. Tambahan: token JWT berumur pendek, rate limit login, validasi input, CSP.

    4. Alur signaling WebRTC

    1. Pengguna login, koneksi Socket.io terautentikasi token.
    2. Klik Video: browser meminta kamera/mikrofon (getUserMedia).
    3. Kirim call:join; server membalas daftar peserta yang sudah ada.
    4. Peserta baru membuat RTCPeerConnection, membuat offer (SDP), mengirim via server ke tiap peserta.
    5. Penerima membalas answer (SDP); keduanya bertukar ICE candidate melalui server.
    6. STUN menemukan alamat publik; jika gagal (NAT ketat) pakai TURN (coturn) sebagai relay.
    7. Koneksi P2P terbentuk, ontrack menampilkan video. Dengan SFU, langkah 4–7 dilakukan terhadap server SFU, bukan tiap peserta.
